### R-1 [A1] 観点: NU-4 の userInfo は公開の C# からは JSON で読めず、比べても何も確かめない
- 根拠:
  - 計画 v2 の 75 行（期待は `userInfo=<JSON>`、JSON は解いて比べる）、12 行、151 行。
  - `Packages/com.jonghyunkim.nativetoolkit/Runtime/iOS/Notification/IosNotificationActionResult.cs`
    - 27 行: 公開されているのは `IReadOnlyDictionary<string,string>? UserInfo` だけで、JSON の文字列は持っていない。
    - 36〜65 行: `ParseFlatJsonObject` は値が文字列でないと 55 行で `break` し、何も取れなければ null を返す。
    - 67〜79 行: エスケープを戻さない。
  - `IosNotificationTextInputActionResult.cs` の 32・39・42 行も同じ形。
  - 1.13.0 の `UnityIosNotificationManager.swift` の 220〜223 行は `JSONSerialization` で JSON を作るので、キーの順は決まっていない。
- 壊れ方:
  - 計画の値 `{"k":1,"nested":{"a":[1,"日本"]}}` は、どのキーが先に来ても最初の値が文字列ではありません。だから `UserInfo` は必ず null です。
  - ハーネスは JSON の文字列を手に入れられません。行は `userInfo=<null>` になり、「実測が違えば記録に書く」で 1.x は null と記録されます。
  - 2.0.0 も同じ構造体と同じパーサーを通るので、やはり `<null>` で「同じ」になります。
  - こうして、R-11 の中心契約（6.3 の印を外すこと、数・入れ子・日本語の往復）は確かめないまま通ります。
  - 文字列の値と文字列でない値を混ぜると、キーの順しだいで結果が変わります。
- 直し案:
  - 照らす値を公開の `UserInfo` の辞書にします。
  - 値はすべて文字列にします（例: `{"k":"v","jp":"日本","slash":"a/b","q":"x\"y"}`）。キーで並べて全件を比べます。パーサーはエスケープを戻さないので、1.x の `a\/b` と 2.0.0 の書き方の違いがここで見えます。
  - 文字列でない値が落ちることは、キーが 1 つの別の値（例: `{"n":1}` → `<null>`）で決まった形として記録します。
  - 2.0.0 の列には「同じ辞書になること。印のキーが残れば辞書が欠ける」と書きます。

1. **A2 / R2-01 — NU-11のM6手順を1.xの公開APIでは実装できない**

   **理由:** 計画:110は `CancelAllScheduledNotifications` の「完了の中」で予約Cを追加しますが、CS:404–408は引数・戻り値とも完了受け手を持ちません。タグの `ios/IosLibrary/IosLibrary/Notification/IosNotificationManager.swift:229–231` もTaskを開始するだけです。計画:114の1秒待機では、M6の完了からの連鎖を検証できません。

   **修正:** 1.xの公開APIでは削除を一覧で確認してからCを追加する手順にし、M6自体は完了を観測できる専用経路、または移行後のC ABIテストへ分けてください。

2. **B 中心契約 / R2-02 — NP-3・18の要求が重なる条件が未定義**

   **理由:** 計画:28、40は連続呼出しをA=0・B=1と予測します。しかしCS:478–480、652–654は、ネイティブ完了の到着時に受け手を取得・消去します。最初の完了が2回目の呼出しより先なら、1.xでもA=1・B=1です。初回R-02の条件制御に関する部分が残り、NT-19の並行要求契約を検証できません。

   **修正:** 最初の完了を保留して両要求を未完了にする制御点を設けるか、重複を確認できた試行と逐次完了した試行を区別してください。無制御ではA=0・B=1を固定期待にしないでください。

3. **B 中心契約 / R2-03 — NP-8が入力検証の欠落を権限拒否で隠せる**

   **理由:** 計画:34は不正値に対する `PERMISSION_DENIED` も記録対象とします。しかし内容setterやtriggerの検証は独立した `INVALID_PARAMETER` 契約です（D2:338–372）。包みが不正値を既定値へ補正しても、その後の権限拒否で区別できません。また計画:46の「正しい値は成功」は、未決Playerでは成立しません（H:231–252）。未知optionも、どの操作・フィールドへ渡すか未指定です。

   **修正:** 不正値は `INVALID_PARAMETER` を必須にし、権限拒否を代替結果にしないでください。正常境界の成功確認は許可後へ移し、各行に完全なfixtureと呼出操作を指定してください。categoryのoptionは登録経路で検証します。

4. **B 中心契約 / R2-04 — PERMISSION_DENIED時のUpdate検証が不足したまま**

   **理由:** 計画:72の拒否済みケースはShow・Scheduleだけで、Updateがありません。計画:31のNP-5bも存在しないIDなので、「既存予約を消さない」を検証できません。D2:379は既存予約の保持を要求し、D2:859は権限なしでは既存予約を作れないため差し替えた経路で検証するとしています。さらにNP-5bはtriggerと照会する一覧が不明です。nil triggerなら即時追加となり、未決時のdeliveredは空とは限りません（タグの `NotificationRepositoryImpl.swift:38–45`、D2:69）。

   **修正:** 拒否済みUpdateの結果とpending/deliveredの前後を追加し、既存予約保持は制御可能なテスト経路へ割り当ててください。NP-5bはtriggerと両一覧の期待を明示してください。

5. **B 中心契約 / R2-05 — NU-12ではNT-17の完了順序と削除効果を確認できない**

## 3. 判断
