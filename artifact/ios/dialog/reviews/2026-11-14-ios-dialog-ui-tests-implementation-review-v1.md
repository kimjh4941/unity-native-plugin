## 1. サブエージェント（重大 0、中 1、軽微 3）

- 結論: 重大な欠陥は無い。テストは計画 v3 のとおりに確かめている。挙動が違うのにテストが通る抜け道も、シミュレーターだけのテストが実機に届く経路も見つからなかった（全文一致と回数、null と空文字、isEnabled、シートの数、ID-17 の状態、`tests --device`・承認・`--tests`・`requireSimulator()` の 4 重の守り、Unity が止まっている間の `dispatch_after` からの呼び出しは main で安全）
- R-1 [中] 実機の承認文が Dialog のテストの中身を正しく書いていない: ID-1〜11・14a・14b の区分 `systemui` の説明は「springboard と通知を押す」だが、実際はハーネス自身のアラートを押し、ID-9 では実機のキーボードで打つ。直し案: `appdialog` のような区分を足す
- R-2 [軽微] ID-14b の遅れがネイティブ（計画は C#）で、1 つ目が出終わったことを確かめていない。遅いと 14a と同じ条件になっても通る。直し案: 2 つ目を呼ぶ直前に 1 つ目が出たかを結果の行に書き、テストで確かめる
- R-3 [軽微] simulatorOnly の名前が tests と合っているかを確かめていない。実機で弾いたときの文言が "Not a UI test" で誤解を招く
- R-4 [軽微] 文書の食い違い: Swift のコメントが「計画の 5 章を直す」と書く（記録は別の文書）。計画の ID-17 の予想に `button=<null>` が無い。記録の文書の「0 回」の出典はレビュー v1 の R-2（v2 は支持しただけ）

## 2. Codex（中 2）

1. 中: 別種類の余分なイベントを見逃す（`HarnessUITestCase.swift:76`）。`finishedLines(id)` は指定した種類だけを比べる。ID-3 で `[confirm@ok] button=OK` に加えて `[dialog@fail] ...` が出ても通る。修正: 6 種類すべての完了行を期待の配列と比べる
2. 中: 成功イベントの誤ったエラー値を見逃す（`DialogScenario.cs:56`）。`ok == true` のとき `error` を捨てている。`("OK", true, "unexpected error")` でも `[dialog@ok] button=OK` になる。修正: 成功のときも error が null でなければ行に書く

## 3. 判断

利用者の指示（2026-11-14、「判断は推奨案でいい」）に従い、すべて直す。

- Codex の 1: Dialog のテストは、6 種類すべての完了の行を期待の配列と比べる
- Codex の 2: 成功のときも、error が null でなければ ` error=<値>` を行に足す（期待の行と食い違って落ちる）
- R-1: 区分 `appdialog`（ハーネス自身のアラートやシートを押す。テキスト欄にはテストの決めた値を打つ）を足し、Dialog のテストに使う
- R-2: 2 つ目を呼ぶ直前に、1 つ目が出ているか（Unity の画面が別の画面を出しているか）を `[twice@event] first-shown=<yes|no>` で書き、テストで `yes` を確かめる。記録の文書に「遅れはネイティブ」と書く
- R-3: runner は simulatorOnly の名前が tests にあることを確かめる。実機の回で弾いたときは「simulator-only」と書き分ける
- R-4: Swift のコメントを記録の文書を指すように直す。計画の版は上書きせず、ID-17 の行の違いと出典の直しを記録の文書に書く
