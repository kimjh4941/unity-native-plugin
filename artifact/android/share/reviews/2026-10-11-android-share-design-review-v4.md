**R4-1 5.3「UnityMain の処理の中から呼んだときの結果のフレーム」の 1.x の列が、端末の 1.x にも当てはまるように書かれている**

- 節: 5.3（v4:426）、J-S2（v4:398）
- 問題:
  - 行は 1.x を「利用者のイベントの購読者や per-call の中から呼ぶと、同じループ（同じフレーム）で結果が出た」と書く。どこで動かしたときかの限定が無い。
  - 1.x の dispatcher の `Update` は、`lock` を持ったまま `while (Count > 0)` を回す（`UnityMainThreadDispatcher.cs:57-62`）。同じループで走るのは、UnityMain が `lock` に入り直して積んだもの（`Enqueue`、`:45`）だけ。
  - 端末の 1.x では、ふつうの結果はすべて Kotlin の main を通る（`UnityAndroidShareManager.kt:317-321`）。
    - プロキシから dispatcher に積むのは Android の main。
    - 動いている `Update` のループが `lock` を放すまで、`Enqueue` は待つ。
    - そのため、結果はループの後（次のフレーム以降）に入る。
  - つまり、同じループで出たのは次の場合だけ。
    - Editor（`TryPrepareCall` が偽。`Mgr:333-336`）。
    - 端末の C# 側の即時の失敗（`pluginInstance` が null、`currentActivity` が null、`Call` の例外。`Mgr:333-349`）。
  - 端末で正しい入力の操作を購読者の中から呼んだときは、1.x も 2.0.0 も次のフレーム以降で、変わらない。
  - 今の行のままでは、移行ガイドが「端末でも、購読者の中から呼んだ結果が 1 フレーム遅れるようになった」と、実際には無い差分を書く。J-11 の「5.3 の行の誤り」に当たる。J-S2 の括弧書き（「1.x の dispatcher は同じループで走らせた」）も同じく範囲が広い。
- 区分: A1（軽い。記述の範囲だけ。仕組みは正しい）

  - v4:426 の 1.x の列を「Editor（と、端末の C# 側の即時の失敗）では、購読者や per-call の中から呼ぶと同じループで結果が出た。端末で Kotlin を通った結果は、Android の main の `Enqueue` がループの終わりを待つので、もとから次のフレーム以降」に直す。

  - 5.1 は、リスナー登録の印を他の static 状態と「1つの `lock`」で守るとしています（v4:377）。
  - J-S6 は登録専用の `lock` を使い、受け口と共有しないとしています（v4:402）。

問題なし: R3-1〜R3-10 と C3-1〜C3-4 は正しく解消されています。追加された Kotlin の行番号、dispatcher と queue、`Share.cpp` の引用も一次資料と整合しています。J-11 の 5.3 に記載済みのエッジケースは欠陥に数えていません。機械整合検査も成功しました。ファイル変更は行っていません。
