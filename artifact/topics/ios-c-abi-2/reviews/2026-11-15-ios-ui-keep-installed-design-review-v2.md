### R-3 [B] 観点: lock の形（取る位置、仕組み、離し方、承認の lock との関係）が決まっていない
- **根拠**
  - v2 35〜36 行: 手順は「1 → 0」の順に並んでいる。lock を承認を使う前に取るのか後に取るのかが読めない。
  - 23 行: 承認の消費にも「リポジトリの外の lock」を使う。36 行の `test_ios.lock` と同じものかどうかは書かれていない。
  - macOS には `flock(1)` が無い（`which flock` は not found。`/usr/bin/shlock` と `/usr/bin/lockf` はある）。
- **壊れ方**
  - 同じファイルを使い、シェルが lock を持ったまま `use-approval` を呼ぶと、Python の側が自分の実行の lock で止まります。実行が必ず失敗します（流せば気づける）。
  - lock を承認を使った後に取ると、取れなかったときに承認が無駄に消費されます。
  - `mkdir` やファイルの有無で作ると、2 つ目の実行が取れずに終わるとき、その trap が lock を消しえます。そうなると 3 つ目の実行が入れます。KILL や再起動の後には古い lock が残り、それ以降の実行がすべて止まります。
- **直し案**
  - 手順 0 を「承認を使う前」に置き、番号を直す。
  - 実行の lock と承認の消費の lock を別のファイルに分ける（承認の lock は Python の `fcntl.flock` で、消費の間だけ持つ）。
  - 実行の lock の仕組みを決める（`shlock -p $$` か、Python の `fcntl` で保持した fd など）。離すのは取った実行だけで、trap の後片付けが済んだ後。古い lock の扱いも書く。

## 2. Codex（を呼ぶエージェント）

v1→v2 の差分と初回指摘への対応を確認し、設計上の修正方針は妥当と判断しました。

- 準備印は承認 marker と分離され、通常ファイル限定・終了時削除が明記されています。承認消費も読み取り・照合・更新を同じ排他区間に置いています（v2:23、36、39）。

- §4 の復元再実行の抑制と、削除確認後の `CLEANED_UP` 設定は、KI-01・KI-02 の原因を解消する方針です（v2:71、72）。

## 3. 判断

A1 が 1 件（サブエージェントの R-1）あるので v3 を作り、3 回目のレビュー（差分だけ）に出す。3 回目でも A1 が残れば、利用者に聞く。3 回目の Codex は、Codex 本体が動くかを先に確かめる。

- **A1（R-1）**: 4 章の 2 つの穴は `verify_unity_ios.sh`（`clean_up_player`、`on_exit`）にも同じ形である。両方のランナーを直す。戻しの印は Unity の段ごとに「始める前に立て、戻し終えたら下ろす」形にする（`verify_unity_ios.sh` には Unity の段が 3 つある）。異常系の確かめも両方のランナーで流す
- **B（直す）**: R-2・R-3（lock は端末か同じシミュレーターに触れる実行がすべて取る。承認を使う前に取る。実行の lock と承認の消費の lock は別のファイル。仕組みは Python の `fcntl` で、取った実行だけが後片付けの後に離す）、R-4（新しい流れでも、消す前に `DEVICE_TOUCHED` を立てる）、R-5（`--dry-run` の一覧に準備を全部と所要時間を入れ、文言を「ハーネスだけにする」に揃える）、R-6（NU-1 の前に照らし、NU-1 が落ちたら待たずに後片付けへ）
- **C（取り込む）**: R-7（NU-1 には変数を付けない。ほかの `xcodebuild` は変数を外して呼ぶ）、R-8（接続の確かめで見る欄は実機の出力で決める）、R-9（`caffeinate -i -w $$`）、R-10（同時消費の確かめは一時フォルダーで）、R-11（実機の OS で入れ物の形が違えば落ちるだけで、押さない）、R-12（`about` の文）、R-13（番号）
