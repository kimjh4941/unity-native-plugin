## 1. サブエージェント

設計書 v3 の 3 回目のレビュー（差分だけ）です。見たのは v3 の 7 章に挙がった変更と、2 回目の指摘が正しく直ったかだけです。ファイルは編集していません。

### R-1 [A2] 観点: 実行の lock を取る位置が「承認を使う前」だけで、EXIT の trap・baseline・最初の Unity の段との前後が決まっていない
- **根拠**
  - v3 35 行: lock の位置は「承認を使う前」としか書いていない。シミュレーターの形には承認が無い。
  - `scripts/test_ios_ui.sh`: `trap on_exit EXIT` は 225 行、`use-approval` は 329 行。シミュレーターの形の `clean_up_apps` は `DEVICE_TOUCHED` を見ずに、3 つのアプリを同じ `SIM_ID` から `simctl uninstall` する（209 行、191〜192 行）。
  - `scripts/verify_unity_ios.sh`: `use-approval` は 418 行。シミュレーターの形では、Editor の 2 段（259〜265 行、上限はそれぞれ 3600 秒）と `record_side_effects_baseline`（169 行）がその前に走る。
- **壊れ方**
  - (a) lock を承認の直前（`test_ios_ui.sh` の 328 行あたり）に置いたとします。2 つ目の `test_ios_ui.sh`（シミュレーターの形）は lock を取れずに exit します。そのとき EXIT の trap が `clean_up_apps` を走らせ、lock を持つ実行のハーネスと runner を同じシミュレーターから消します。lock を持つ実行には、3 章 68 行のシミュレーターの `--keep-installed` も入ります。v2 の R-14 で lock が防ぐはずだった「待っている実行のハーネスを消す」が、そのまま起きます。待っている側の次のテストが落ちるので、気づくことはできます。
  - (b) `verify_unity_ios.sh` のシミュレーターの形で 418 行の前に置くと、Editor の 2 段（最長 2 時間）が lock の外で `ProjectSettings` を書き換えます。
  - (c) baseline を取った後に lock を取る場合です。先の実行が、その間の Unity の段の途中で終わると、その変更は baseline に「前からあった変更」として入ります。2 つ目の実行が同じパスを変えても戻さないので、変更が黙って残ります（173 行の比べ方による）。
- **直し案**
  - どちらのランナーでも、引数を照らした直後、`require_clean_ios_plugins`・`record_side_effects_baseline`・EXIT の trap より前に取る、と書く（これで承認より前にもなる）。
  - 3 章のシェルの確かめに「lock を取れずに止まる実行では、後片付けも戻しも走らない」を足す。

### R-2 [B] 観点: lock を持つ子プロセスがいつ終わり、どのシグナルで終わらないかが決まっていない
- **根拠**
  - v3 35 行: 「fd を持つ小さな見張りの子プロセスが実行の終わりまで持つ」「離すのは取った実行だけで、後片付けの後」「KILL や再起動の後に古い lock は残らない」。
  - `flock(2)`: lock は、その open file description を持つ fd が全部閉じるまで残る。親が KILL されても、子は launchd に引き取られて動き続ける。
  - bash(1) の Signals: job control の無いシェルが裏で起こしたコマンドは、SIGINT と SIGQUIT だけを無視する。TERM と HUP は既定の動きのまま。
  - 今の `on_exit` の `trap '' INT TERM HUP`（`test_ios_ui.sh` 212 行）が効くのは親だけ。
- **壊れ方**
  - (a) 見張り役やツールの時間切れが親だけを KILL すると、子が lock を持ち続けます。それ以降の実行は、すべて「取れない」で止まります。「KILL の後に古い lock は残らない」が成り立ちません（次の実行で気づけます）。
  - (b) 端末を閉じたとき（前面のプロセスグループに HUP が届く）や、グループに TERM を送ったときは、子がすぐ終わって lock が離れます。一方、親の `on_exit` は、3 つのアプリの uninstall（1 つ 120 秒まで）と戻しの途中です。「後片付けの後に離す」が崩れ、その間に始まった実行と、後片付けや戻しが重なります。
  - (c) 子が lock を取れたかどうかを親に返す形が無いので、「取れなければ、承認を使わずに止まる」を作れません。
- **直し案**
  - 子は TERM・HUP・INT を無視する。終わるのは、親の終了（kqueue の `NOTE_EXIT`、または `getppid()` の変化を短い間隔で見る）か、親からの明示の解放のときだけ、と書く。pipe の EOF で解放するなら、xcodebuild や Unity などの子孫に受け継がれない fd にする。
  - 子は「取れた／取れなかった」を 1 行で返し、親はそれを読むまで先へ進まない。
  - 3 章に次の 2 つの確かめを足す: 「親を KILL した後、次の実行が lock を取れる」「グループに TERM や HUP を送っても、後片付けが終わるまで lock が離れない」。

### R-3 [B] 観点: 1.2 の手順 6・7 で止まったとき、報告と終了コードが決まっていない
- **根拠**
  - v3 39 行（手順 5）と 42 行（手順 8）は、流さなかったテストを `did not run (an earlier test failed)` と出す、と書いている。
  - 40 行（手順 6 の時間切れと `.cancel`）と 41 行（手順 7 の照らしや接続が駄目なとき）は、「テストを始めずに後片付けへ進む」だけ。
  - 今の `test_ios_ui.sh` では、`failures` が増えるのは `build_all`・`run_one`・`clean_up_apps` の失敗のときだけ（342・346・351 行）。0 なら `PASSED` を出して 0 で終わる（360 行）。
- **壊れ方**: 時間切れか `.cancel` で止めて後片付けが成功すると、NU-1 だけが通った状態で `PASSED`・終了コード 0 になりえます。NU-4・5・7・11 の行は出ません。3 章の「待ちの時間切れ」の確かめは、後片付けに進むことしか見ないので通ってしまいます。
- **直し案**: 手順 6・7 で止まったときも、NU-4・5・7・11 をそれぞれ `did not run (…)` と出し、失敗として数える（終了コードは 0 にしない）、と書く。3 章の時間切れと取り消しの確かめで、終了コードも照らす。

### R-4 [B] 観点: シミュレーターの `--keep-installed` の流れが 1.2 に無い
- **根拠**
  - 1.2 の題と使い方は `--device --keep-installed` だけ（25・28・29 行）。
  - 手順 4 の `remove_from_device` と `DEVICE_TOUCHED`、手順 7 の `devicectl` は実機だけのもの。
  - 3 章 68 行は、シミュレーターで `--keep-installed` を流すと書いている。

- **壊れ方**: 手順どおりに作ると、シミュレーターの形には起動の段がありません。`DEVICE_ID` が空のまま `remove_from_device` を呼ぶか、入れるところで落ちます（流せば気づけます）。
- **直し案**: 1.2 にシミュレーターの形の違いを書く。
  - 手順 2・7 は飛ばす
  - 手順 3 の後に起動する（`SIM_BOOTED_BY_US` を含む）
  - 手順 4 は `simctl` で消してから入れる
  - 使い方に `--device` の無い行を足す

### R-5 [C] 観点: `verify_unity_ios.sh` の Editor の 2 段の間には戻しが無く、「段ごとに戻し終えたら下ろす」が editmode では書けない
- **根拠**: `verify_unity_ios.sh` の 261・263 行は 2 段を続けて走らせ、戻すのは 264 行の 1 回だけ。v3 75 行は「Unity の段ごとに、始める前に印を立て、戻し終えたら下ろす」「Unity の段が 3 つある」と書いている。
- **壊れ方**: editmode には「戻し終えた」点がありません。editmode の後で印を下ろすと、playmode が始まるまでの間に止められたとき、editmode の書き換えが残ります（その間はごく短い）。
- **直し案**: editmode の後にも戻しを足すと書く。または、Editor の 2 段を 1 つの段として扱い、261 行の前に印を立てて 264 行の戻しの後に下ろす、と書く。

## 2. Codex

第2回R-1は設計上修正されています。両ランナーを対象に、Unityの各段の開始前に復元印を立て、復元後に下ろす方針が明記されました（v3:73）。

1. B / R3-01：ロック保持子プロセスの終了条件が未定義
   理由：v3:35の、全実行で取得・承認消費前に取得・別ファイルで承認消費を排他する方針は妥当です。ただし「fdのロックなのでKILL後も残らない」は、親シェルだけがKILLされた場合には保証されません。親終了後も子プロセスは存続し得ます（macOS _exit.2:71）。逆に保持子だけが終了した場合の実行停止も未定義です。
   修正：親消滅時に保持子が終了する仕組み、通常のシグナルでは後片付け完了まで保持する仕組み、保持子異常終了時の実行停止を定義し、異常系の検証を追加してください。

2. B / R3-02：最初のテストより接続確認が後になる
   理由：v3:39でNU-1を実行しますが、tunnel・DDIの確認は待機後の手順7（v3:41）だけです。追加されたdevice_guardは承認・HEAD・作業木の照合であり、接続確認を代替しません（scripts/ios_ui_runner.py:269）。規則はテスト直前の接続確認を要求しています（/Users/jonghyunkim/Desktop/native-toolkit/agent-rules/device-testing.md:48）。
   修正：NU-1直前にも時間制限付きの接続確認を置き、待機後にも再確認してください。
