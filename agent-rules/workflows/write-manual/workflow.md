引数: $ARGUMENTS

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力で対象を確定する（必須）
   - ダイアログで「対象機能名を入力してください（例: notification）」と促す
   - ダイアログで「対象マニュアルバージョンを指定してください」と促す
     - `manual/` 配下の既存バージョン一覧を候補として提示する
     - 新規バージョンを入力した場合:
       - `manual/` 配下の最大バージョンフォルダをコピーする
       - コピー先フォルダ名を入力された新規バージョンに変更する
       - （例: 最大が `1.2.0` で `1.3.0` を入力 → `manual/1.2.0/` を `manual/1.3.0/` としてコピー）
       - コピー直後にコミット・プッシュを行う（この時点ではまだ内容は前バージョンのまま）
         - これにより、以降の編集が「前バージョンからの差分」として git 上で明確になる
         - コミットメッセージ例: `chore(manual): copy manual/1.2.0 to manual/1.3.0 as baseline`
   - ダイアログで「実行モードを選択してください」と促す:
     - マニュアル生成 + 公開: ステップ3へ進む（言語・ソースファイル入力が続く）
     - 公開のみ: ステップ3〜9をスキップしてステップ10へ進む
   - 「マニュアル生成 + 公開」を選択した場合のみ、以下の入力を行う:
     - ダイアログで「生成する言語を選択してください」と促す（デフォルト: en / ja / ko 全て）
     - ダイアログで「ソースファイルを指定してください（複数選択可）」と促す
       - `artifact/results/<feature>/` 配下の次のファイルを候補として提示する:
         - `*-implementation-result*.md`
         - `*-sample-scene-result*.md`
       - 入力がない場合は `artifact/plans/<feature>/` 配下の `*-implementation-plan*.md` も候補に含める
       - 同一ドキュメントの改訂版がある場合は最も大きいバージョンのみを候補にする
       - 複数ファイルを選択した場合は全て読み込んで内容を統合する

3. ソースファイルを読み込み、前提情報を抽出する（必須）
   - 指定されたファイルから次を抽出する:
     - 対象 OS とプラットフォーム
     - 公開 API 一覧（メソッド名・シグネチャ・用途）
     - パラメータ・戻り値・エラー契約
     - 実装済みのスコープ（in-scope 機能）

4. 結果ファイルと実装の矛盾を検証・修正する（必須）
   - ステップ3で読み込んだ結果ファイルに記載された内容を、実際のソースコードと照合する
   - 照合対象:
     - テストケース名の一致（テストファイルを直接読んで全関数名と比較）
     - テスト件数の一致
     - 変更ファイル一覧の実在確認
     - API名・シグネチャ・エラーコードの一致
   - 矛盾が見つかった場合:
     - 矛盾箇所と修正内容をユーザーに提示する
     - 結果ファイルを修正してから次のステップへ進む
   - 矛盾がない場合はそのまま次のステップへ進む

5. 既存マニュアルを参照してスタイルを固定する（必須）
   - `manual/<version>/index.md` を読み込み、リンク構造とセクション構成を把握する
   - 同バージョンまたは直近バージョンの同種マニュアルファイル（例: `notification.md`）を読み込む
   - 次の観点でスタイルを固定する:
     - ファイル先頭の言語切り替えリンクの形式
     - 目次の構成
     - プラットフォームセクションの分け方
     - コード例の詳細度（クラス名・メソッド呼び出し・コールバック処理まで含む本番品質）
     - 画像参照の形式（`images/<platform>/<feature>/xxx.png`）
   - 対象機能の ExampleController コードを特定して読み込む（必須）:
     - 読み込み対象の例（機能名に対応するファイルを検索する）:
       - `Packages/com.jonghyunkim.nativetoolkit/Runtime/UI/<platform>/<feature>/*ExampleController.cs`
     - 画面に表示される操作セクションの順序を把握し、マニュアルのセクション構成をそれに合わせる
       （例: ExampleController が Permission → Show → Update/Cancel → Schedule → Query → Badge → Category の順なら、マニュアルも同順にする）
     - APIコール時の実際のパラメータ値・ID文字列・定数・コールバック処理をそのまま抽出する
       （例: `id = "mac-sample-notification"` / `.IsSuccess` が void の場合は void のまま使う）
     - 画像プレースホルダーのファイル名は ExampleController の操作名に対応させる
       （例: `Example_MacNotificationManager_RequestPermission.png`）
     - ExampleController のコードと乖離したコード例は使用しない。乖離すると画面キャプチャとコードが一致しなくなる

6. マニュアルを生成する（必須）
   - ステップ3・5（ExampleController コード含む）の内容をもとに、指定言語ごとにマニュアルを生成する
   - 出力先:
     - 英語: `manual/<version>/<feature>.md`
     - 日本語: `manual/<version>/<feature>.ja.md`
     - 韓国語: `manual/<version>/<feature>.ko.md`
   - 各マニュアルに含める内容:
     - 言語切り替えリンク（先頭）
     - 上位 index.md へのリンク
     - 目次
     - プラットフォームごとのセクション
     - API ごとのコード例（実行可能な本番品質の C# コード）
     - 画像参照（以下の HTML 形式でプレースホルダー挿入）
       ```html
       <p align="center">
           <img src="images/<platform>/<feature>/xxx.png" alt="xxx" width="400" />
       </p>
       ```
       - `alt` 属性はファイル名（拡張子なし）とする
       - Markdown の `![alt](path)` 形式は使用しない
       - ファイル名は ExampleController の操作セクションに対応させる（ステップ5で抽出した名称を使用）
       - コードブロックの直後に配置する（見出し直下ではなくコードの下）
       - 以下のセクションには画像を挿入しない:
         - ボタンを押してもUIに変化が現れない操作（例: Cancel 系）
         - エラー系セクション（コードとログで説明が完結するため）
         - イベント受信セクション（コードのみで完結するため）
   - 既存ファイルがある場合はユーザーに上書き確認を行い、承認なしで上書きしない

7. `manual/<version>/index.md` を更新する（必須）
   - 英語・日本語・韓国語の各 `index` ファイル（`index.md` / `index.ja.md` / `index.ko.md`）に、新しいフィーチャーページへのリンクを追加する
   - 既にリンクが存在する場合はスキップする

8. `README.md` / `README.ja.md` / `README.ko.md` を更新する（必須）
   - 新規バージョンの場合: 3ファイル内のバージョン番号参照（例: `1.2.0`）を新バージョンに更新する
     - 対象箇所の例:
       - Manual / Published docs のバージョン参照
       - `docs/<version>/manual/` へのリンク
   - 新規バージョン・既存バージョンのどちらでも、以下を必ず行う:
     - 対象 OS のフィーチャーセクション（例: `### macOS`）に、今回実装した機能の箇条書きを追記する
       - 既に記載がある場合はスキップする
     - `## Planned Features` セクションから、今回実装した機能を削除する
       - 例: macOS 通知を実装した場合は `- Notifications (macOS)` を削除する
     - パッケージの概要文（冒頭 2〜3 行）が特定機能のみを列挙した限定的な表現になっている場合は、実装済み機能を包括する表現に更新する
       - 例: 「ダイアログ操作をシングルトン API で扱えます」→「ダイアログ・通知などのネイティブ機能をシングルトン API で扱えます」

9. 実行確認を行う
   - ユーザーに次を確認する: 「このマニュアルで進めますか？」
   - 選択肢:
     - 採用する: ステップ10へ進む
     - 修正する: 指摘内容を反映してステップ6へ戻る
     - キャンセル: ここまでの作成ファイルは保持したまま終了（ユーザー向けドキュメントは公開しない）

10. ユーザー向けドキュメントを公開する（必須）
    - `./scripts/publish_docs.sh <version>` を実行する
    - `<version>` にはステップ2で確定したバージョン番号を使用する
    - スクリプトの実行結果を確認し、失敗した場合はエラー内容を報告する

11. 出力ルール

- コード例は ExampleController のコードを正とする（ID・パラメータ値・コールバック処理は ExampleController のものをそのまま使用）
- コード例は既存マニュアルと同水準の本番品質（実行可能・クラス名・コールバック処理まで含む C# コード）
- 画像は `<p align="center"><img src="images/..." alt="..." width="400" /></p>` 形式のプレースホルダーを挿入する。Markdown の `![alt](path)` 形式は使用しない
- 画像はコードブロックの直後に配置する（見出し直下ではない）
- 翻訳は機械的直訳ではなく、各言語の自然な表現を使う
- 絵文字は使用しない
- 不確実な API 仕様は断定せず、要確認として明記する
