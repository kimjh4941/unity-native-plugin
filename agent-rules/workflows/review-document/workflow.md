引数: $ARGUMENTS

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でパラメータを確定する（必須）
   - ダイアログで「レビュー対象のファイルを指定してください」と促す
   - 入力がない場合は以下の候補を提示:
     - `artifact/designs/<feature>/` 配下の `*-design*.md` を探索し、同一ドキュメントの改訂版（`-v2`, `-v3` など）がある場合は最も大きいバージョンのみ
     - `artifact/designs/<feature>/` 配下の `*-sample-scene-design*.md` を探索し、同一ドキュメントの改訂版がある場合は最も大きいバージョンのみ
   - バージョンサフィックスがないファイルは `v1` とみなし、`vN` が存在する場合は `vN` を優先する
   - ユーザーが選択したファイルパスを確定する

3. 対象ファイルを読み込む（必須）
   - 指定されたファイルを読み込む
   - ファイル種別（実装計画書 vs サンプルシーン計画書）を判定する
   - ファイルサイズが大きい場合は「ファイルを読み込みました」と報告する

4. レビュー観点を設定する（必須）
   - **実装計画書（`*-design*.md`）の場合:**
     - native-toolkit API 確認結果の網羅性（抜け漏れがないか）
     - C# 側の呼び出し方針（DllImport / AndroidJavaObject の選択）の妥当性
     - Manager + Bridge パターン準拠性（層・依存方向）
     - 変更ファイル一覧の正確性（新規作成 / 既存変更 / 非変更の分類）
     - エラーケース一覧の網羅性と返却仕様（isSuccess / errorMessage）の整合性
     - スレッド契約・メモリ契約の明示
     - テスト方針の網羅性（EditMode / PlayMode / 手動確認の分担）
     - IL2CPP 制約・コンパイルガードへの言及
     - **プラットフォーム独立性**（`agent-rules/coding-rules/common.md`「命名: OS 接頭辞と、共通ファイルを作らない方針」）
       - **P1**: 新規ファイル名すべてに OS 接頭辞（`Android` / `Ios` / `Mac` / `Windows`）が付いているか。**`Tests/` 配下のテストファイル名・クラス名も対象**。機能ディレクトリに接頭辞なしのファイルを作っていないか
       - **P1b**: 1 つのテストファイルが複数プラットフォームの型を扱っていないか。テストのコンパイルガードが対象型と一致しているか
       - **P2**: 「既存変更」欄に**他プラットフォームのファイルが挙がっていないか**。共有化・改名・リファクタで既存実装に触れる計画になっていないか
       - **P3**: 既存型を再利用・共有と判断した箇所が、**プラットフォームガードの有無ではなく実際の利用箇所**に基づいているか
       - **P4**: `Runtime/Common/` への新規追加が、機能ロジックではなく横断インフラに限られているか
       - **P5**: クラスガード（`#if X \|\| UNITY_EDITOR`）と P/Invoke ガード（`#if X && !UNITY_EDITOR`）の二重構造になっており、Player ビルドに他プラットフォームのコードが入らない設計か
       - **既知の逸脱 11 件を前例として引用していないか。** `ClipboardOperationResult` などの接頭辞なし型は Android / macOS 専用であり、共有型ではない（`artifact/OS_PREFIX_VIOLATIONS.md`）
       - P1〜P5 の違反は **A1 区分**として扱う。後から直すと破壊的変更になるため、C（記述整合）に落とさない
   - **サンプルシーン計画書（`*-sample-scene-design*.md`）の場合:**
     - 実装結果ファイルとの整合性（公開 API・エラー契約の反映）
     - 画面要件の網羅性（機能一覧・操作導線・エラー表示）
     - 既存 ExampleController との整合性（共通パターンの維持）
     - 変更ファイル一覧の正確性
     - 入力バリデーション方針の明示
     - 手動確認観点の網羅性

5. レビューを実施する（必須）
   - ステップ4で設定した観点をもとに、対象ファイルを自分でレビューする
   - 以下の構造で結果をまとめる:
     - 強み（strengths）
     - 改善点（improvements）: セクション名・問題点・severity（high/medium/low）・改善提案
     - 不足項目（missing_items）
     - 総合評価（overall_assessment）

6. レビュー結果を整理・表示する（必須）
   - 強み（strengths）を表示する
   - 改善点（improvements）を severity 順に表示する:
     - `high`: 高優先度
     - `medium`: 中優先度
     - `low`: 低優先度
   - 不足項目（missing_items）を表示する
   - 総合評価を表示する

7. レビュー結果をファイルに保存する（必須）
   - 保存先: `artifact/reviews/<feature>/YYYY-MM-DD-<os>-<feature>-<document-type>-review-vN.md`
     - `<os>`: 対象 OS（例: `android` / `ios` / `macos` / `windows`）
     - `<feature>`: 対象ファイルのパスから自動抽出（例: `notification`）
     - `<document-type>`: ファイル種別に応じて `design` / `implementation-feature` / `sample-scene-design` など
     - `vN`: レビュー結果のバージョン。**必ずバージョンを付与し、既存ファイルは上書きしない**
     - 例: `artifact/reviews/notification/2026-05-16-macos-notification-implementation-feature-review-v1.md`
   - **バージョン採番ルール（必須）:**
     - 保存先ディレクトリ内で、同じ `YYYY-MM-DD-<os>-<feature>-<document-type>-review` プレフィックスを持つ
       既存ファイルを探索する
     - 既存がなければ `v1` で新規作成する
     - 既存がある場合は、最も大きい `vN` を見つけて `v(N+1)` で新規作成する（**既存ファイルは上書きしない**）
     - バージョンサフィックスがない旧形式のファイル（`...-review.md`）が存在する場合は `v1` とみなす
   - ファイル形式（Markdown）:
     ```
     # レビュー結果

     - 日付: YYYY-MM-DD
     - 対象ファイル: <レビュー対象ファイルパス>
     - 機能名: <feature>
     - プラットフォーム: <ファイルから抽出>

     ---

     ## 強み

     <strengths を箇条書きで列挙>

     ## 改善点

     ### 高優先度

     <high severity の improvements>

     ### 中優先度

     <medium severity の improvements>

     ### 低優先度

     <low severity の improvements>

     ## 不足項目

     <missing_items を箇条書きで列挙>

     ## 総合評価

     <overall_assessment>
     ```
   - 保存後、保存パスを明示する

8. ユーザーに改善実施を確認する（必須）
   - 次の選択肢を提示:
     - 「改善版を自動生成する」: Step 9 へ進む
     - 「一部のみ改善する」: 改善対象を指定させる
     - 「レビュー結果のみで終了」: Step 11 へ進む

   **止める基準（必須）**

   指摘の件数ではなく**種類**で判定する。

   | 区分 | 内容 | 扱い |
   |---|---|---|
   | **A1. 実装フェーズで気づけない** | この通り実装すると動作・API・契約が変わり、**かつコンパイルもテストも通ってしまう** | **止めない。直して再レビュー** |
   | **A2. 実装フェーズで気づける** | 契約は変わるが、コンパイルエラー・テスト失敗・型エラーとして必ず表面化する | **直さない。実装結果ファイルにチェックリストとして転記して先へ** |
   | **B. 検証手段を変える** | テスト設計・DoD・テストシームの穴 | 中心契約なら直す。網羅系は記録して先へ |
   | **C. 記述の整合だけ** | 章間の相互参照・件数・ID・型名・引用行番号・章節番号 | **機械照合に回す。手で直さない** |

   A1 と A2 の切り分けは「実装者がこの通り書いて、コンパイルとテストで気づけるか」で判定する。

   - 気づける例: 未定義シンボルを呼ぶ擬似コード、複数スロットのうち 1 本を決め打ちする記述（対応するテストが落ちる）
   - 気づけない例: コールバック登録を解放する条件の誤り（機能が静かに死に、手動確認まで発覚しない）

   **A1 が 0 になったら止める。** ただし次を満たすこと。

   1. **レビュアーを替えて 1 回通していること**（別モデル・別プラットフォームの観点を 1 回入れる）
   2. **機械照合（`scripts/check_design_consistency.py`）が通っていること**
   3. **直さない残件（A2 / B / C）が、文書自身に理由つきで明記されていること**

   **指摘 0 件を目標にしない。** 擬似コードを詳細化するほど、その詳細に対する指摘が新たに生まれる。設計書が答えるべきなのは「後から変えると高くつく決定」だけで、それ以外は実装・コンパイル・テスト・コードレビューという、より速く確実なフィードバックループに任せる。

   **サーキットブレーカー**

   | 状況 | 意味 |
   |---|---|
   | 5 ラウンドを超えた | 基準そのものか、レビュー対象の切り方を疑う |
   | 同じ種類の指摘が 3 回続く | 個別の修正ではなく、それを生む仕組みを直す |

   > 根拠: macOS clipboard の設計レビューが 6 ラウンド回った（design-v1 〜 v6）。A 区分は
   > 6 → 9 → 1 → 3 → 2 と収束したが、C 区分（数の表記・章節番号・引用行番号の食い違い）は
   > 毎ラウンド発生し、手で直しても次の版で再発した。native-toolkit 側でも同じ機能で同じ
   > 現象が記録されており、機械照合を入れてから止まっている。

9. レビュー結果をベースに改善版を生成する（必須・選択時のみ）
   - 元ファイルを読み込む
   - レビュー結果の改善点・不足項目を統合する
   - 改善版を Markdown で生成する
   - **重要: 改善版のファイル名は別名にする**
     - 元ファイル: `YYYY-MM-DD-<os>-<feature>-implementation-feature-v1.md`
     - 改善版: `YYYY-MM-DD-<os>-<feature>-implementation-feature-v2.md`（`-v2` サフィックスを追加）
     - 実装計画書・サンプルシーン計画書の種別ごとに対応

10. 改善版を保存する（必須・改善実施時）
   - 改善版を元ファイルと同じディレクトリに保存する
   - 保存パスを明示する
   - 保存後、改善版ファイルを現在の VS Code で新しいタブとして開いて表示する

11. 出力ルール:

- レビュー結果は構造化（強み → 改善点 → 不足項目 → 総合評価）で提示する
- severity レベルは視覚的に区別する
- 改善版が生成される場合、元ファイルと改善版の関係を明確にする（`-v2` サフィックス）
- 改善対象の詳細は箇条書き中心で書く
- 不確実な指摘は「要検証」として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない

12. 実行確認を行う

- ユーザーに次を確認する:
  - 改善版が出力された場合: 「この改善版をベースに進めますか？」
  - レビュー結果のみの場合: 「レビューは完了しました。」
- 改善版がある場合の選択肢:
  - 実行する: 改善版を確定
  - 修正する: 追加の修正を指定
  - キャンセル: レビュー結果のみで終了
