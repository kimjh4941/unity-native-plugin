引数: $ARGUMENTS

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する
   - `version=X.Y.Z` が含まれていれば対象バージョンとして使用する
   - `lang=ja` または指定なしは出力言語を日本語、`lang=en` は英語として扱う
   - `--strict` が含まれていれば警告も停止扱いにする

2. 対象バージョンを確定する（version が未指定の場合のみ）
   - `manual/` 配下の既存バージョン一覧を候補として提示する
   - 最大バージョンを既定値として提示する

3. 検査を実行する
   - `./scripts/verify_manual.sh <version>` を実行する
   - `--strict` 指定時は `./scripts/verify_manual.sh <version> --strict` を実行する
   - スクリプトが 7 項目を検査し、終了コードで停止項目の有無を返す

   | # | 検査 | 区分 | 内容 |
   |---|---|---|---|
   | 1 | 画像参照 | 停止 | `images/...` が実体に解決するか |
   | 2 | サンプル整合 | 警告 | コード例の識別子リテラルが ExampleController に、型・メンバーが `Runtime/` に実在するか |
   | 3 | アンカー | 停止 | `[](#anchor)` が見出しに解決するか |
   | 4 | バージョン参照 | 停止 | Git URL・`docs/` リンク・バージョン見出しが `<version>` と一致するか |
   | 5 | 文体 | 警告 | 日本語が です・ます体、韓国語が 합니다体 か |
   | 6 | 言語差分 | 警告 | 3 言語で画像・見出し数が揃っているか |
   | 7 | docs 同期 | 停止 | `docs/<version>/` が `manual/<version>/` と一致し、`docs/latest` が最新を指すか |

4. 結果を解釈してユーザーに提示する
   - スクリプトの出力をそのまま貼るのではなく、次の観点で整理する:
     - **今回の作業で作り込んだもの**と**前バージョンから引き継いだもの**を区別する
       - 判定方法: `manual/<前バージョン>/` に対して同じスクリプトを実行し、差分を取る
       - 引き継ぎ分は今回のリリースを止める理由にならない場合が多い
     - 停止項目は、修正するか・別途対応にするかをユーザーに確認する
     - 警告項目は、誤検出の可能性を添えて提示する（下記の限界を必ず添える）
   - 検査7 が FAIL の場合は、`./scripts/publish_docs.sh <version>` を実行すれば解消するかを先に判断する
     （`manual/` 側の編集漏れではなく単なる再公開忘れであることが大半）

5. 停止項目がある場合の確認
   - 「停止項目があります。どうしますか？」を確認する:
     - 修正する: 該当箇所を修正し、ステップ3 へ戻る
     - 別途対応にする: `artifact/` に軽量な md として記録し、終了する
     - 無視して続行: そのまま終了する（リリース時に再度検出される）

## 検査の限界（提示時に必ず添えること）

### 検査2 が検出できないもの

**マニュアル側が「書き忘れた」場合は検出できません。**

ExampleController に存在する API や値は、マニュアルがそれを省略しても「実在する」ため
差分になりません。検出できるのは逆方向（マニュアルが実在しない値・API を書いた場合）だけです。

```
検出できる: マニュアルが GetSnapshotAsync と書き、Runtime に存在しない
検出できない: ExampleController が CheckForegroundChange を使い、マニュアルが省略している
```

操作の網羅性は目視で確認してください。

### 検査2 が対象にしないもの

表示用の文字列（`"Copied"` などの UI 文言）は検査しません。マニュアルが説明のために独自の
文字列を書くのは正当であり、全リテラルを対象にすると誤検出が実用に耐えません。

対象は次の 2 種類に限定しています。

- 識別子形リテラル（ドットを含む。`public.png` / `com.jonghyunkim.nativetoolkit.example.custom` など）
- パッケージの型・メンバー（`Ios` / `Android` / `Mac` / `Windows` で始まる名前）

**Swift の引数ラベル相当の検査は行いません。** C# の名前付き引数は必須ではなく、
`$"emails: {count}"` のような文字列補間と区別できないため、誤検出しか生みません。

また、コードフェンスの言語が `csharp` のものだけを見ます。`xml` の AndroidManifest 断片は
サンプルシーンのコードではないため対象外です。

### 検査3 が検出できないもの

**解決はするが行き先が間違っているアンカーは検出できません。**

同名見出しが複数あるページで `-1` / `-2` の対応がずれている場合、リンクとしては有効なため
差分になりません。`notification.ko.md` の `예약 알림`（3 か所）のように、同名見出しが並ぶ
ページを編集したときは目視で確認してください。

### 検査5 の誤検出

体言止めや箇条書きの断片を常体と誤認することがあります。指摘された行を必ず目視で確認して
から修正してください。

### 検査7 の前提

`docs/` は `scripts/publish_docs.sh` が `manual/` からコピーしたものです。`docs/` を直接
編集する運用は想定していません。`.DS_Store` は差分から除外しています。

## 意図的な例外の登録

検査2 で「利用者が自分の値に置き換える前提」の値を許容する場合は、
`agent-rules/workflows/verify-manual/SAMPLE_CONFORMANCE_IGNORE.txt` に追記します。

実際に動く操作の ID・UTI・パラメータ値は例外にしないでください。
ExampleController と乖離すると、コード例と画面キャプチャが一致しなくなります。

## 呼び出し元

このワークフローの実体は `scripts/verify_manual.sh` です。次の 2 箇所から使われます。

- `/verify-manual`（単体起動。本ワークフロー）
- `agent-rules/workflows/release/workflow.md` ステップ3 のリリース前チェックリスト

`write-manual` からは呼びません。マニュアル作成時点ではスクリーンショットが未取得のため、
検査1 が必ず失敗するためです。画像を配置した後に本ワークフローを実行してください。
