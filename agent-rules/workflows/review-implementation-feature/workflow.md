引数: $ARGUMENTS

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - PR番号が含まれていれば `pr=<number>` として扱う
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. レビュー対象のコードを確定する（必須）
   - `git rev-parse --abbrev-ref HEAD` を実行して現在のブランチ名を取得する
   - `git diff develop...HEAD` を実行して develop ブランチとの差分を取得する
   - 差分が空の場合はユーザーに「develop との差分がありません。ローカルの未コミット差分を対象にしますか？」と確認し、承認された場合は `git diff` を実行する
   - PR番号が `$ARGUMENTS` に含まれている場合は `gh pr view <number>` と `gh pr diff <number>` を優先して使用する

3. インタラクティブ入力で参照ファイルを確定する（必須）
   - ダイアログで「レビュー対象機能の実装計画ファイルを指定してください」と促す
   - 実装計画ファイルの入力がない場合は次を候補として提示する
     - `artifact/designs/<feature>/` 配下の `*-design*.md`
   - ダイアログで「レビュー対象機能の実装結果ファイルを指定してください」と促す
   - 実装結果ファイルの入力がない場合は次を候補として提示する
     - `artifact/results/<feature>/` 配下の `*-implementation-feature-result*.md`
   - ダイアログで「対象プラットフォームを選択してください」と促す（ラジオボタン: Android / iOS / macOS / Windows）

4. プロジェクトルールを読み込む（必須）
   - `agent-rules/coding-rules/common.md` を読み込み、共通実装方針を把握する
   - `agent-rules/coding-rules/csharp.md` を読み込み、C# コーディングルールを把握する

5. 実装計画・実装結果ファイルを読み込む（必須）
   - 指定された実装計画ファイルを読み込み、次を把握する:
     - エラーケース一覧と返却仕様
     - テスト方針（正常系・異常系・境界値）
     - 変更ファイル一覧と実装詳細
   - 指定された実装結果ファイルを読み込み、次を把握する:
     - DoD達成状況
     - 計画との差分
     - 未実施テストと理由

6. コードレビューを実施する（必須）
   以下の観点で分析する:

   **実装計画との整合性**
   - Manager + Bridge パターン準拠性（層・依存方向の違反がないか）
   - 変更ファイル一覧の正確性（計画記載の変更対象と実際の変更が一致しているか）
   - テスト方針の網羅性（計画のテスト観点がすべて実装されているか）
   - エラーケース一覧が実装されているか
   - 各エラーの返却仕様（isSuccess / errorMessage）が実装と整合しているか

   **正確性**
   - ロジックの誤り、条件分岐の抜け漏れ
   - エラー契約の実装漏れ（isSuccess / errorMessage 対応の整合性）
   - isSuccess == true のとき errorMessage == null の保証

   **プロジェクトルール準拠**
   - `agent-rules/coding-rules/common.md` への適合
   - `agent-rules/coding-rules/csharp.md` への適合
   - 命名規則・ディレクトリ規約との整合性

   **プラットフォーム独立性**（`common.md`「命名: OS 接頭辞と、共通ファイルを作らない方針」）
   - **P1**: 追加したファイル名と型名すべてに OS 接頭辞が付いているか。**`Tests/Runtime/` / `Tests/PlayMode/` のテストファイル名・クラス名も対象**。機能ディレクトリに接頭辞なしのファイルを作っていないか
   - **P1b**: 1 つのテストファイルが複数プラットフォームの型を扱っていないか。テストのコンパイルガードが対象型と一致しているか
   - **P2**: **他プラットフォームの既存ファイルを変更していないか。** `git diff --name-only <base>` の差分に、対象プラットフォーム以外の `Android*` / `Ios*` / `Mac*` / `Windows*` が含まれていないかを機械的に確認する
   - **P3**: 既存型を再利用した箇所で、**ガードの有無ではなく実際の利用箇所**を確認して単一専用か共有かを判定しているか
   - **P4**: `Runtime/Common/` への追加が横断インフラに限られているか
   - **P5**: クラスガードと P/Invoke ガードが二重構造（`#if X \|\| UNITY_EDITOR` / `#if X && !UNITY_EDITOR`）になっており、Player ビルドに他プラットフォームのコードが入らないか
   - **既知の逸脱 11 件を前例として引用していないか**（`artifact/OS_PREFIX_VIOLATIONS.md`）
   - P1〜P5 の違反は **A 区分**として扱う（止める基準の表を参照）

   **Bridge 実装品質**
   - スレッド安全性（UnityMainThreadDispatcher 経由の確認）
   - メモリ管理（アンマネージドバッファの確実な解放）
   - IL2CPP 互換性（MonoPInvokeCallback の static 宣言等）
   - コンパイルガード（`#if UNITY_ANDROID` 等）の適切な使用

   **既存 API 互換性**
   - 破壊的変更の有無
   - 公開 API のイベントシグネチャ変更

   **テストカバレッジ**
   - 正常系・異常系・境界値の網羅状況
   - エラー全ケースのテスト有無

   **コード品質**
   - 重複コードの有無
   - 不要な複雑さ・抽象化の過剰
   - パフォーマンス上の懸念（毎フレーム呼び出し等）

   **セキュリティ**
   - 入力バリデーションの有無
   - 機密情報の扱い

7. レビュー結果を出力する（必須）
   以下の構造で出力する:

   ### レビュー概要
   - PR / 差分の目的と変更内容のサマリー

   ### 重大な問題（high）
   - 修正必須の問題を列挙する（なければ「なし」）

   ### 改善提案（medium）
   - 推奨する改善点を列挙する

   ### 軽微な指摘（low）
   - スタイル・命名などの軽微な指摘を列挙する

   ### 実装計画整合性チェック
   - Manager + Bridge パターン準拠: ○ / △ / ×
   - 変更ファイル一覧との一致: ○ / △ / ×
   - テスト方針の網羅性: ○ / △ / ×
   - エラーケース全実装: ○ / △ / ×
   - 返却仕様との整合: ○ / △ / ×

   ### プロジェクトルール適合チェック
   - common.md 準拠: ○ / △ / ×
   - csharp.md 準拠: ○ / △ / ×
   - Bridge 実装品質（スレッド安全性・メモリ管理）: ○ / △ / ×
   - 既存 API 互換性: ○ / △ / ×

   ### テストカバレッジ
   - カバーできている観点と不足している観点を示す

   ### 総合評価
   - LGTM / 要修正（軽微） / 要修正（重大） のいずれかで示す

8. レビュー結果ファイルを保存する（必須）
   - 保存先: `artifact/reviews/<feature>/`
   - ファイル名: `YYYY-MM-DD-<os>-<feature>-implementation-feature-review-vN.md`
   - 同名が存在する場合は `vN` をインクリメントし、既存ファイルを上書きしない
   - 最低限、次を含める:
     - レビュー対象（ブランチ名 / PR番号 / diff）
     - 実装計画・実装結果ファイルのパス
     - レビュー結果（step 7 の出力全体）
     - 総合評価

9. 出力ルール

- 指摘は具体的なファイルパスと行番号を可能な限り示す
- プロジェクトルール（common.md / csharp.md）由来の指摘は明示する
- 不確実な指摘は「要確認」として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない

10. 修正対応を確認する（必須）
   ユーザーに次を確認する:
   - 「このレビュー結果をもとに修正を行いますか？」
   - 選択肢:
     - 修正する: 指摘内容を反映して `implement-feature` workflow に準じて修正する
     - レビュー結果のみで終了: 修正は行わず終了する

   **止める基準（必須）**

   指摘の件数ではなく**種類**で判定する。**設計レビュー（`review-document`）の基準とは
   区分が異なる。** 設計レビューは「実装フェーズで気づけるか」で A1 / A2 を分けるが、
   実装レビューの対象は既にコンパイルもテストも通ったコードなので、A2 は存在しない。
   コンパイルとテストを通り抜けたうえで振る舞いを変えるものは、すべて A である。

   | 区分 | 内容 | 扱い |
   |---|---|---|
   | **A. 振る舞いを変える** | 利用者から見た動作が変わる。誤ったエラーコード、無言の失敗、コールバックの未発火、スロット・ハンドルのリーク、契約違反 | **止めない。直して再レビュー** |
   | **B. 検証手段を変える** | テストや検査の穴。中心契約が未検証、テストシームが機能していない | **中心契約なら直す。網羅系は記録して先へ** |
   | **C. 記述だけを変える** | 実装計画書・XML ドキュメントコメント・実装結果ファイルとの不一致 | 安ければ直す。記録して先へでも可 |

   **A が 0 になったら止める。** ただし次の 3 条件をすべて満たすこと。

   1. **レビュアーを替えて 1 回通していること。** 同一レビュアーが 3 ラウンド続けて A を
      出さなくなったら、収束ではなく視点の固着を疑う
   2. **追加したテストが、壊すと落ちることを確認済みであること。** 通ることの確認では足りない。
      **同じ種類の指摘が続くときは、個別のテストを足すのではなくその規則を疑う**
   3. **直さない残件が、実装結果ファイルに理由つきで明記されていること。** 「未実装」を
      通過扱いにしない

   **指摘 0 件を目標にしない。** 修正はレビュー面積を増やす（テストを足せばテスト自身が
   対象になる）ため、反復で 0 には収束しない。

   **サーキットブレーカー**（基準ではなく、立ち止まる合図）

   | 状況 | 意味 |
   |---|---|
   | 5 ラウンドを超えた | 基準そのものか、レビュー対象の切り方を疑う |
   | 同じ種類の指摘が 3 回続く | 個別の修正ではなく、それを生む仕組みを直す |

   > 根拠: native-toolkit の macOS clipboard で実装レビューが 12 ラウンド回った。同一
   > レビュアーの 3 ラウンドは 1H → 1H → 1H と減って収束に見えたが、レビュアーを替えた次の
   > ラウンドで 4H / 7M / 7L が出て、うち 2 件は製品の実不具合だった（無言に失敗する paste
   > button、Unity への誤ったエラーコード）。**件数の減少は収束ではない。**
