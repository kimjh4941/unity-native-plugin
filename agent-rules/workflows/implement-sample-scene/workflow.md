引数: $ARGUMENTS

以下の手順を実行してください。

1. `$ARGUMENTS` を解析する（最小限）
   - `lang=ja` または指定なしは出力言語を日本語として扱う
   - `lang=en` が明示的にあれば英語

2. インタラクティブ入力でサンプル計画を確定する（必須）
   - ダイアログで「サンプルシーン計画ファイルを指定してください」と促す
   - 入力がない場合は次を候補として提示する:
     - `artifact/designs/<feature>/` 配下の `*-sample-scene-design*.md`
   - 指定された計画ファイルを読み込み、画面要件・変更ファイル一覧・実装詳細・手動確認観点を把握する

3. サンプルシーンを実装/更新する（必須）
   - 計画ファイルの実装詳細に従い、ExampleController に機能ごとの操作 UI を追加する
   - 入力バリデーションとエラー表示を追加する
   - 実行結果（成功/失敗）を再現可能な形で表示する
   - 既存 API 互換性を維持し、破壊的変更は明示承認なしで行わない
   - `.meta` ファイルは Unity が自動生成するため作成しない

4. 検証手順を追加する（必須）
   - 手動確認手順をドキュメント化する（観点・操作・期待結果）
   - 未実施ケースは理由を明記する

5. ビルド・実行確認を行う（必須）

- Unity Editor でコンパイルエラーがないことを確認する
- 実行可能な確認を行い、失敗時は修正する
- 実機依存で未確認の項目は明示する

6. 実装結果を保存する（必須）

- 保存先: `artifact/results/<feature>/`
- ファイル名: `YYYY-MM-DD-<os>-<feature>-implement-sample-scene-result-vN.md`
- 既存ファイルがある場合は `vN` をインクリメントし、上書きしない
- 最低限、次を記載する:
  - 変更ファイル
  - 実装したサンプル機能
  - ビルド/実行結果
  - 手動確認観点 / 未実施項目（理由付き）

7. 出力ルール

- 計画ファイル由来の内容と、サンプル実装時の追加判断を明確に分離する
- 共通実装パターンに対して、どこを維持しどこを拡張したかを明記する
- 変更対象ファイルは可能な限り具体パスで示す
- テスト結果は手動確認観点と未実施項目（理由付き）を必ず示す
- 不確実な事項は断定せず、要検証として明記する
- 文章は簡潔に、箇条書き中心で書く
- 絵文字は使用しない

8. 実行確認を行う

- ユーザーに次を確認する: 「このサンプル実装結果を採用して、次工程へ進めますか？」
- 選択肢:
  - 実行する: この実装結果を採用して終了 → review-implementation-sample-scene スキルへ引き継ぐ
  - 修正する: 指摘内容を反映して再実装
  - キャンセル: ここまでの修正差分は保持したまま、終了
